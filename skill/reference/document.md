Generate a `DESIGN.md` file at the project root that captures the current visual design system of a React Native / Expo app, so AI agents generating new screens stay on-brand and platform-correct.

The output is a `DESIGN.md` whose body is a TypeScript **`tokens.ts` module** (light + dark color objects, type scale, space scale, radius scale, platform-split shadow, motion durations) plus prose context (Overview, Components, Platform Notes, Do's and Don'ts). **Tokens are normative; prose explains how to apply them.**

The token module is the source of truth. `DESIGN.md` embeds it as a code block, and downstream commands (`craft`, `audit`, `animate`, `colorize`, `harden`) read it to stay on-brand. Section headers below are fixed in name and order so those commands can locate them by string match.

## The output: one file, one shape

```markdown
---
name: <App Name>
description: "<one sentence describing the design character>"
---

# Design System: <App Name>

## Overview
[2–3 paragraphs: atmosphere, north star, what it rejects.]

## Tokens
```ts
// tokens.ts — generated by /impeccable-native document
const light = { /* ... */ };
const dark  = { /* ... */ };
export const tokens = { color: { light, dark }, type, space, radius, shadow, motion };
export type ColorScheme = typeof light;
```

## Components
[3–6 RN component snippets: PrimaryButton, Card, Input, etc.]

## Platform Notes
[iOS vs Android shadow, font defaults, safe areas, Dynamic Type.]

## Do's and Don'ts
[Forceful guardrails. Every PRODUCT.md anti-reference shows up here as a Don't.]
```

Rules that matter:

- **Emit a compiling TypeScript module.** Colors are hex (`#RRGGBB`) or rgba strings. Spacing, radius, font sizes, and line heights are unitless numbers — RN reads them as density-independent pixels. Font weights are union literals (`'400'`, `'500'`, `'600'` …) with `as const` so they narrow to `TextStyle['fontWeight']`.
- **Light AND dark live side by side.** Every color token has a `light` and a `dark` value. A single `useTheme()` hook reads `useColorScheme()` once at the provider level and returns the active set. Components consume `colors.x` — they never branch on color scheme themselves.
- **Shadow is platform-split.** Each shadow token carries both `.ios` (`shadowColor` / `shadowOffset` / `shadowOpacity` / `shadowRadius`) and `.android` (`elevation`). Consumers spread the correct one via `Platform.OS === 'ios' ? token.ios : token.android`.
- **Type scale is fixed sizes**, not fluid. iOS Dynamic Type and Android font scaling enlarge text at the OS level; the design system sets the base, the user sets the multiplier.
- **NativeWind is a secondary surface.** When the flavor detector reports `styling: "nativewind"`, the `tokens.ts` module is still the source of truth. Offer to mirror the same tokens into `tailwind.config.ts` so utility classes resolve to identical values — don't replace the StyleSheet output with class strings.

- **Scan mode** (default): the project has a token file, a theme module, or rendered screens. Extract, then confirm descriptive language. Use when there's code to analyze.
- **Seed mode**: the project is pre-implementation (fresh teach, no components built yet). Interview for five high-level answers, write a minimal DESIGN.md marked `<!-- SEED -->`. Re-run in scan mode once there's code.

Decide by scanning first (Scan mode Step 1). If the scan finds no theme module, no token file, no recurring StyleSheet values across components, offer seed mode; don't silently switch. `{{command_prefix}}impeccable-native document --seed` forces seed mode regardless of code presence.

## Scan mode: auto-extract, then confirm descriptive language

### Step 1: Find the design assets

Run the flavor detector first if not already run this session:

```bash
node {{scripts_path}}/detect-rn-flavor.mjs
```

The detected `styling` field tells you where tokens are likely to live. Then search the codebase in priority order:

1. **Existing token file**: `tokens.ts`, `theme.ts`, `colors.ts`, `design-tokens.ts`, usually under `src/`, `theme/`, `design/`, or `constants/`. Read the full file; capture colors, type, space, radius, shadow, motion.
2. **Themed design library**: Restyle, Tamagui, Unistyles, Dripsy — each exposes a `createTheme({...})` call or equivalent. Read the object as-is.
3. **NativeWind / Tailwind config**: `tailwind.config.{js,ts,mjs}` `theme.extend` for colors, fontFamily, spacing, borderRadius. Map the Tailwind step keys onto the numeric scale (`p-4` → `space['4']` = 16).
4. **`StyleSheet.create` across components**: scan `**/*.tsx` and tally values that appear three or more times. Those are de facto tokens whether or not a token file exists.
5. **`useColorScheme` / `Appearance` calls**: confirms light/dark intent. Note which colors flip and which stay anchored across schemes.
6. **`expo-font` / `useFonts` registration**: the custom font families the app actually loads, plus the weights registered.
7. **Reanimated / Moti durations**: `withTiming(value, { duration: 250 })` literals repeated across files are motion tokens in disguise.
8. **Brand assets**: `assets/icon.png`, `assets/splash.png`, `assets/adaptive-icon.png`. Sample the dominant hue if the codebase doesn't expose an accent token.

### Step 2: Auto-extract what can be auto-extracted

Build a structured draft from the discovered values. For each token class:

- **Colors**: separate `light` and `dark` variants. Group by role: surfaces (`background`, `surface`, `surfaceSubtle`), text (`textPrimary`, `textSecondary`, `textTertiary`, `textInverse`), accent (`accent`, `accentSubtle`, `accentStrong`), semantic (`error`, `warning`, `success`, `info`), borders (`border`, `borderStrong`). If the project only has one accent, express it as accent + neutrals; don't invent a secondary.
- **Typography**: map observed sizes/weights to a fixed scale: `display`, `headline`, `title`, `body`, `label`, `caption`. Capture font family if loaded via expo-font; otherwise leave `fontFamily` undefined to use platform defaults (SF Pro on iOS, Roboto on Android). Capture letterSpacing and lineHeight in absolute numbers, not multipliers.
- **Space**: extract the scale steps actually used (`4`, `8`, `12`, `16`, `24`, `32`, `48`, `64`, `96`). Numeric keys keyed by step (`'1'`, `'2'`, `'3'`, …) make the calling code self-documenting — `tokens.space['4']` reads as 16 dp.
- **Radius**: `sm`, `md`, `lg`, `xl`, `full` (9999). Capture only the steps the project uses; don't fabricate.
- **Shadow**: extract the project's shadow vocabulary, then split each level into `.ios` (using `shadowColor`/`shadowOffset`/`shadowOpacity`/`shadowRadius`) and `.android` (using `elevation`). If the project is flat and uses borders/tonal layering instead, that's a valid answer; state it explicitly and skip the shadow scale.
- **Motion**: extract durations and any custom easings. Default scale: `fast` (150), `normal` (300), `slow` (500). Capture custom easings as Reanimated `Easing` references in a comment, since they can't be serialized.

### Step 2b: Stage the `tokens.ts` module

From the auto-extracted values, draft the TypeScript module now (you'll embed it in DESIGN.md in Step 4). Goals: it should compile against `@types/react-native` as-is, with no manual fixes.

- Use `as const` on font weights so they narrow to the `TextStyle['fontWeight']` union.
- Numeric values are plain numbers; RN reads them as density-independent pixels.
- Color values are `#RRGGBB` or `rgba(...)`. If the source uses another color space, resolve it to hex during extraction so the module compiles and ships.
- Export both the `tokens` object and a `ColorScheme` type (`export type ColorScheme = typeof light`) so consumers can type the `useTheme()` return.
- Skip any token group the project doesn't have. An empty `shadow: {}` scale or fabricated motion tokens pollute the system.

### Step 3: Ask the user for qualitative language

The following require creative input that cannot be auto-extracted. Group them into one `AskUserQuestion` interaction:

- **Creative North Star**: a single named metaphor for the whole system ("The Editorial Sanctuary", "The Field Notebook", "The Quiet Console"). Offer 2-3 options that honor PRODUCT.md's brand personality.
- **Overview voice**: mood adjectives, aesthetic philosophy in 2-3 sentences, anti-references (what the system should not feel like).
- **Color character** (for auto-extracted colors): descriptive names for accent and key neutrals ("Burnt Sienna", "Cooled Bone", not `accent` or `neutral-50`). Suggest 2-3 options per key color based on hue and saturation.
- **Elevation philosophy**: flat / layered / lifted. If shadows exist, is their role ambient (atmosphere) or structural (hierarchy cue)?
- **Component philosophy**: the feel of buttons, cards, inputs in one phrase ("tactile and confident" vs. "quiet and precise" vs. "playful and springy").
- **Motion stance**: restrained (state changes only), responsive (feedback + transitions), or choreographed (orchestrated entrances, scroll-driven). Reanimated and gesture-driven UIs default to choreographed; this is a stated stance, not a default.

Quote a line from PRODUCT.md when possible so the user sees their own strategic language carry forward. Reference the **Platform Fidelity** field from PRODUCT.md when discussing the component philosophy: a `cupertino-everywhere` stance shapes button radii and motion differently than a `material-everywhere` stance.

### PrimaryButton

```ts
import { StyleSheet, Pressable, Text } from 'react-native';
import { tokens } from './tokens';
import { useTheme } from './useTheme';

export function PrimaryButton({ label, onPress }: { label: string; onPress: () => void }) {
  const colors = useTheme();
  return (
    <Pressable
      onPress={onPress}
      style={({ pressed }) => [
        styles.base,
        { backgroundColor: pressed ? colors.accentStrong : colors.accent },
      ]}
      accessibilityRole="button"
      accessibilityLabel={label}
    >
      <Text style={[styles.label, { color: colors.textInverse }]}>{label}</Text>
    </Pressable>
  );
}

const styles = StyleSheet.create({
  base: {
    minHeight: 48,                                 // meets iOS 44pt and Android 48dp
    paddingHorizontal: tokens.space['6'],
    paddingVertical: tokens.space['3'],
    borderRadius: tokens.radius.md,
    alignItems: 'center',
    justifyContent: 'center',
  },
  label: { ...tokens.type.label },
});

## Platform Notes

**Shadow.** iOS uses `shadow*` props (`shadowColor`, `shadowOffset`, `shadowOpacity`, `shadowRadius`). Android uses `elevation`. Tokens above include both; spread the correct one via `Platform.OS === 'ios' ? tokens.shadow.md.ios : tokens.shadow.md.android`.

**Font family.** Type tokens omit `fontFamily` to use platform defaults (SF Pro on iOS, Roboto on Android). Add `fontFamily` only when loading a custom brand font via `expo-font`. Load fonts before the splash screen clears or first paint will flash the system font.

**Safe areas.** Use `useSafeAreaInsets()` from `react-native-safe-area-context` to pad for notches, Dynamic Island, and the home indicator. Compose with tokens: `paddingBottom: insets.bottom + tokens.space['4']`. Never hardcode device-specific inset values.

**Dynamic Type / TalkBack font scaling.** Test layouts at 2x font scale. RN scales text by default unless `allowFontScaling={false}` is set; don't disable it without a strong reason.

**Platform fidelity stance.** Reflect PRODUCT.md's `Platform Fidelity` field: `cupertino-everywhere` → iOS-style radii (8–14), spring motion; `material-everywhere` → larger radii (16–28), ripple feedback; `cupertino-android-pragmatic` → iOS-style on iOS, Material defaults on Android; `custom-cross-platform` → one design language both platforms accept.

### Do

- **Do** route every color through `useTheme()`. The hook reads the active scheme once at the provider; components consume `colors.x`.
- **Do** put every reusable style in `StyleSheet.create`, including styles handed to `FlatList` `renderItem`. Stable style references keep list virtualization fast.
- **Do** animate `transform` and `opacity`. Both run on the UI thread under Reanimated and stay smooth at 60–120 fps.

- **Do** tint near-black and near-white toward the brand hue. Warm or cool blacks read as intentional on OLED; pure black reads as a default.

## Style guidelines

- **Tokens first, prose second.** Token values live in the `tokens.ts` code block; prose names them and explains where they're used. The code block is the single source of truth for values.
- **Cite PRODUCT.md anti-references by name** in the Do's and Don'ts section. If PRODUCT.md lists *"Material 3 defaults"* or *"another white-background todo app"* as anti-references, the DESIGN.md Don'ts should repeat those phrases verbatim so the visual spec enforces the strategic line.
- **Five fixed sections.** Overview, Tokens, Components, Platform Notes, Do's and Don'ts. Motion durations live inside `tokens.motion`; motion stance lives in Overview; per-animation choreography belongs in `animate.md`. Layout decisions and responsive behavior fold into Components.
- **Descriptive > technical**: "Generous rounding (20pt)" beats "borderRadius: 20" alone. Include the technical value, lead with the description.
- **Functional > decorative**: for each token, explain WHERE and WHY it's used, not just WHAT it is.
- **Exact values in parens or inline**: hex codes, point/dp values, font weights — always the number alongside the description.
- **Use Named Rules**: `**The [Name] Rule.** [short doctrine]`. These are memorable and citable. Aim for 1–3 per system (Overview, Tokens, or Components).
- **Be forceful.** The voice of a design director. "Forbidden", "never", "always", not "consider", "might", "prefer". Match PRODUCT.md's tone.
- **Concrete anti-pattern tests.** A one-sentence audit test beats a paragraph of principle. *"If the button looks the same on iOS and Android down to the shadow blur radius, the platform-split shadow token was not applied."*
- **Group colors by role**, not by hex order or hue order. Surface → Text → Accent → Semantic → Border is the canonical ordering.

## Pitfalls

- **iOS-only shadow tokens.** A shadow without the Android `elevation` branch looks lifted on iOS and flat on Android. Every shadow level needs both.
- **A `dark` object that's missing keys.** TypeScript will catch it if you type `dark: typeof light`, but a half-filled dark scheme produces invisible text the moment a user flips their system theme.
- **Inline `useColorScheme()` ternaries scattered through components.** The hook should be called once at the theme provider; components read `colors.x`. Otherwise dark-mode bugs accumulate per component.
- **Type tokens with `lineHeight < fontSize`.** RN clips descenders. Line heights below the font size produce clipped text at 2x Dynamic Type the moment a user enlarges system fonts.
- **Fabricating tokens the project doesn't use.** If the codebase has one accent and no semantic colors, ship one accent. Empty scales and invented roles pollute the system and the agents that read it.
- **Inventing components that don't exist.** If the project only has Buttons and Cards, only document those. Synthesise canonical primitives only in seed mode, where the commitment is explicit.
- **Overwriting an existing DESIGN.md silently.** Always show the user the existing file and confirm refresh / merge / overwrite first.
- **Duplicating PRODUCT.md content.** DESIGN.md is strictly visual and token-level. Strategy, users, brand voice live in PRODUCT.md and are read by reference, not copied.
- **Renaming sections even slightly.** `## Tokens` not `## Design Tokens`; `## Do's and Don'ts` not `## Guidelines`. Downstream commands (`craft`, `audit`, `animate`) locate sections by exact header match.
- **Adding sections beyond the five.** Layout, Motion, Responsive Behavior, Accessibility — fold these into Overview (philosophy), Components (per-component behavior), or Platform Notes (device-level concerns). The five-section shape is the contract.
